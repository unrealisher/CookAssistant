# План первой версии CookAssistant

## Цель и решения

Сделать адаптивный сайт для личной коллекции рецептов. Он будет запускаться вручную на твоём компьютере и открываться с телефона через домашнюю Wi‑Fi сеть. Нативное мобильное приложение и перенос на личный сервер — следующие этапы, после первой версии.

Стек: **React + TypeScript + Vite**, **Python + FastAPI**, **SQLite**. Vite поддерживает шаблон React/TypeScript, а проверку типов нужно запускать отдельной командой в CI. FastAPI проверяет структуру запросов и публикует описание API; SQLite подходит для локального запуска как файл базы. [Vite](https://vite.dev/guide/), [FastAPI: модели запросов](https://fastapi.tiangolo.com/tutorial/body/), [FastAPI: SQLite](https://fastapi.tiangolo.com/tutorial/sql-databases/). Redux в первой версии не нужен.

## Поведение и интерфейс

- На странице добавления — большое текстовое поле. На телефоне рецепт можно надиктовать встроенным микрофоном клавиатуры; аудио сайт не записывает.
- После нажатия «Сохранить» текст отправляется облачному ИИ. ИИ выделяет название, ингредиенты, количества и единицы, шаги, время, температуру и теги. Рецепт сохраняется без экрана подтверждения. Если обработка не удалась, текст остаётся в поле и доступна повторная попытка.
- Сохраняются исходный продиктованный текст и разобранная версия. Если ИИ что-то понял неверно, рецепт можно вручную поправить целиком: переименовать, добавить или удалить ингредиенты и шаги, изменить количества, время, температуру и теги.
- Количества и единицы свободные: например, `500 г`, `2 штуки`, `по вкусу`. Время и температура остаются частью шага; таймеры и масштабирование порций не нужны.
- Теги назначаются автоматически, по возможности повторно используются существующие. Их можно добавлять, менять и удалять вручную. Поиск работает по названию и тегам, но не по ингредиентам.
- Рецепты личные. При первом локальном запуске создаётся единственный аккаунт владельца, после чего открытая регистрация отключается. Фото, заметки и совместный доступ не входят в первую версию.

API с самого начала проектируется для будущего мобильного клиента:

- `Recipe`: название, исходный текст, список ингредиентов, шаги, теги, даты создания и изменения.
- `Ingredient`: название, количество и свободная единица измерения.
- `Step`: текст шага и необязательные значения времени и температуры.
- Версионированные маршруты `/api/v1`: настройка первого аккаунта и вход; создание рецепта из текста; список с поиском; просмотр, изменение и удаление рецепта. Контракт API публикуется через OpenAPI, из него генерируются типы для TypeScript.
- Для разбора текста — OpenRouter Responses API со структурированным выводом по JSON Schema; модель по умолчанию — `openai/gpt-4o-mini`. Модель можно заменить через `COOKASSISTANT_OPENROUTER_MODEL`, ключ хранить только в локальном `.env` под именем `OPENROUTER_API_KEY`. Стоимость зависит от выбранной модели. [Structured Outputs](https://openrouter.ai/docs/features/structured-outputs), [каталог моделей](https://openrouter.ai/models).

## Этапы разработки

Каждая задача разработки — отдельная ветка. После каждого кодера отдельные read-only субагенты-ревьювер и тестер проверяют подзадачу. После успешных проверок подзадач новая пара ревьювера и тестера проверяет полный интегрированный diff и функциональность по критериям приёмки. PR на master сливается после успешного завершения всех обязательных CI-проверок и настроенных проверок ревью. После мержа нужно перейти на master, обновить его и удалить рабочие worktree и локальные ветки; удалённую ветку PR удалить, если GitHub не удалил её автоматически. Обнаруженные несвязанные баги оформляются отдельными подробными issues на GitHub.

1. **Основа проекта и CI.** Создать публичный GitHub-репозиторий; добавить React/TypeScript и FastAPI, проверку здоровья сервера, инструкции по запуску, шаблон PR и GitHub Actions. Так как сейчас в папке нет Git-репозитория, этот стартовый коммит создаст основу для последующих PR.
2. **Данные и личный аккаунт.** Добавить SQLite с миграциями, создание первого владельца, вход и выход, закрытые API-маршруты и модели рецепта. База и настройки хранятся вне Git-репозитория.
3. **Сайт и ручное редактирование.** Сделать мобильный список рецептов, карточку и форму изменения. Добавить ингредиенты, шаги, теги, поиск и удаление рецептов.
4. **ИИ-разбор и автосохранение.** Добавить обработку свободного текста, автоматическое создание рецепта и тегов, повторное использование существующих тегов. Ключ OpenRouter хранить только в локальном `.env` как `OPENROUTER_API_KEY`; в CI использовать имитацию ИИ, без платных запросов.
5. **Локальный запуск и переносимость.** Подготовить PowerShell-скрипты для сборки, запуска и обновления сайта на Windows. Создать резервное копирование и восстановление SQLite, проверить миграцию базы и описать перенос проекта на личный сервер.

## Проверки и выпуск

- GitHub Actions на каждом PR: backend-тесты `pytest`, проверки Python-форматирования и линтинга, frontend-тесты, проверка TypeScript, сборка и браузерные проверки основных сценариев.
- Набор русскоязычных примеров для ИИ: разные единицы измерения, пропущенные количества, несколько тегов, время и температура в шагах. В CI ответы ИИ подменяются тестовыми; перед приёмкой этапа ИИ отдельно проверяется на реальных примерах с настроенным API-ключом.
- Браузерный сценарий: создать владельца, войти, отправить текст рецепта, открыть сохранённый рецепт, исправить ингредиент, шаг и тег, найти его по названию и тегу.
- При выпуске сохранить резервную копию базы до миграции. Проверить сайт с телефона в домашней сети, включая ввод текста через клавиатурную диктовку.
- После зелёных проверок PR сливается, а локальный скрипт обновляет сборку на компьютере. Сервер запускается вручную и доступен, пока компьютер включён. Доступ ограничен домашней сетью; порт не публикуется в интернет. Перед доступом извне на личном сервере нужно включить HTTPS.
- В репозитории не хранить API-ключ, базу рецептов или реальные данные. Стоимость запросов OpenRouter зависит от выбранной модели.
